Alert dialog

The browser's own
interruption, in house type.

A modal that stops the page and asks one question. Not a toast, not a notification — nothing else can happen until it is answered. It is a native <dialog>, so the top layer, the focus trap, the ESC key, the inert background and the focus return to whatever opened it are the platform's job, not mine.

3 tones 1 node, reused promise API serialised queue

01

Three tones

Same anatomy, same motion, same keyboard contract. Only the glyph colour and the primary button change — exactly how the action button's variants work.

notealert()

Tell them something

One button. Nothing to decide — the dialog exists only because the message cannot wait for a quieter surface. Primary is .btn-ink.

askconfirm()

Ask for a decision

Two buttons, a reversible outcome. Primary is .btn-accent and takes focus — this is the one accent in the view.

riskno undo

Confirm a loss

Destructive and irreversible. Primary is .act.v-danger, Cancel takes focus, and the scrim does not dismiss.

There is no success tone. A completed action reports itself on the button that started it — the action button already owns success. A dialog that appears only to say "done" is an interruption with nothing to interrupt.

02

With one input

The prompt() shape. One field, never two — a dialog that needs a second field is a form, and a form belongs on a page. Enter submits, ESC cancels, the label sits left with its hint right.

Name a snapshot

Resolves with the trimmed string, or null if cancelled — same contract as the browser's.

Type-to-confirm

A risk tone whose primary stays disabled until the typed value matches. The guard lives in the machine, not in the button.

03

When the answer does work

If confirming kicks off a request, the primary is a stateful .act, never a static .btn. The dialog holds itself open through pending, closes on resolve, and reports failure in place — so the user never loses the question they were answering.

Succeeds after 1.4s

Cancel disables, ESC is ignored, the scrim is inert. Nothing can strand a request mid-flight.

Fails after 1.4s

The button returns to idle, the reason prints under the copy, and the dialog stays exactly where it was.

05

Rules

A modal spends the visitor's attention without asking. These keep the bill small.

  • oneNever more than one dialog on screen. A second call queues behind the first, the way the browser serialises its own.
  • oneOne question per dialog. Two questions is a page.
  • titleThe title is the question. Never "Are you sure?" — say what happens.
  • verbThe primary label is the verb from the title. Discard, not OK. Delete, not Yes.
  • focusask focuses the primary. risk focuses Cancel — a safe default when the key is already under a finger.
  • scrimScrim click dismisses note and ask. It never dismisses risk, and never anything mid-pending.
  • accentThe dialog is its own view, so it may carry the one .btn-accent — but a risk dialog carries none. Destruction is never the accent colour.
  • asyncAsync primary is .act, static primary is .btn. Never substitute one for the other.
  • neverNo auto-dismiss, no timers, no stacking, no close X in the corner, no success tone, no scroll behind the scrim.
  • lastIf the answer can be undone instead of confirmed, undo is the better design. Reach for this last.
