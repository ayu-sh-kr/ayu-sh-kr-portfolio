dota-workspace

A monorepo toolchain for building web-component apps.

8 packages, one workspace

Authoring web components meant repeating the same boilerplate in every app. I wanted the ergonomics of a modern framework without giving up the platform — no virtual DOM, no lock-in, just the browser's own component model with the sharp edges filed off.

A core, then satellites

dota-core defines the component model — reactivity, lifecycle, templating. Everything else is a thin package that builds on it: dota-router for routing, dota-rest for typed data, dota-ui for primitives. You adopt only what you need, and nothing pulls in the rest.

Note Because it's all standard custom elements, an app built on dota keeps working even if I stop touching the framework tomorrow. That outlives framework churn — the whole reason I built it this way.

One pipeline, every package

A single Vite-based toolchain builds, versions, and publishes all eight packages together. A change to the core ripples out in one command, and the whole workspace stays in lockstep. Here's the shape of a component in userland:

TypeScriptimport { component, html } from 'dota-core'

component('user-card', ({ name }) => html`
  <article class="card">
    <h3>${name}</h3>
  </article>
`)

No decorators, no build-time magic beyond bundling — what you write is close to what the browser runs.

A framework you can walk away from is a framework worth trusting.

It runs this site

The portfolio, the blog, and this case study are all built on dota. That's the strongest proof I can offer that the ergonomics hold up past a toy example — I use it for everything I ship.

Why this stack

Three choices carried the project: Web Components for longevity, TypeScript because the API is only as good as its types, and Vite because a monorepo build that's slow is a monorepo build you stop running. Everything else followed from those.
