Distributed locks in Redis, without the folklore

Ayush · Backend engineer

TL;DR

  • SETNX alone is not a lock — you need expiry and ownership.
  • Most "lock" problems are actually idempotency problems.
  • If correctness matters more than latency, use the database.

Every distributed locks tutorial starts the same way: SET key value NX PX 30000, a triumphant paragraph, and no mention of what happens when your process pauses for 31 seconds. This post is about the second part.

The lock you actually wrote

Here is the minimal version that isn't wrong on day one — acquire with a random token, release only if you still own it:

Kotlinval token = UUID.randomUUID().toString()
val ok = redis.set("lock:payout:$userId", token,
                   SetArgs().nx().px(30_000))

try {
    if (ok) processPayout(userId)
} finally {
    releaseIfOwner("lock:payout:$userId", token)
}

The token matters. Without it, a slow process can delete a lock that a faster process re-acquired — and now two workers are paying out the same user.

A lock without ownership checks is just a suggestion with a TTL.

When you don't need a lock at all

In two years of running Sacrena's backend, most places I reached for a lock, what I actually needed was an idempotency key on the operation. Locks serialize; idempotency forgives. The second is almost always cheaper to reason about at 3am.
