# Docker Sandbox Kit and AWS Lambda MicroVMs make private AI coding agents more practical

Imagine asking a coding agent to fix a failing test. It reads the repository, installs a package, runs a shell command, and opens a pull request. For a personal project, that can feel like a faster editor. For a company, each step raises a harder question: **whose machine, which credentials, and what can leave the network?**

Two announcements give that question a more concrete answer. On September 24, [Docker announced the open Sandbox Kit Spec](https://www.docker.com/blog/docker-sandbox-kit-spec-cncf/) and said it is bringing the specification to the CNCF. Earlier this year, [AWS launched Lambda MicroVMs](https://aws.amazon.com/about-aws/whats-new/2026/06/aws-lambda-microvms/) for isolated execution of user and AI-generated code. They are separate products, but together they show where organizational agentic development is heading: **agents as managed workloads**, with reviewed access and dedicated execution environments.

## First, make the agent's requests visible

An ordinary container image tells you what software is inside. A Docker **Kit** also declares the host access, credentials, and volumes the agent requests. Docker packages that descriptor, the agent, and its tools as an OCI image. A team can put it in an existing registry, scan and sign it, pin a version, and review a changed permission alongside a changed agent. If version two asks for a new credential or network destination, there is something specific to question in the diff.

That is a useful shift for platform teams. Today, an agent's effective access can be scattered across a developer's laptop, environment variables, a CI runner, and a dashboard. A portable declaration gives reviewers a place to start. **The declaration is not the enforcement:** the runtime must actually apply those limits. Docker's [v3 Kits are currently Early Access](https://docs.docker.com/ai/sandboxes/customize/), and an OCI image being portable does not mean every container runtime already understands or enforces its agent permissions. Docker is taking the specification to the CNCF; broad cross-runtime adoption remains to be demonstrated.

## Then, give the work its own machine

AWS approaches the execution side. A Lambda MicroVM is a dedicated [Firecracker-based environment](https://docs.aws.amazon.com/lambda/latest/dg/lambda-microvms-guide.html) that can run builds, tests, package installation, and other code an agent generates. AWS says it provides VM-level isolation and can suspend and resume a session for up to eight hours. Unlike a short-lived function invocation, this gives an agent room to work through a task while separating that work from a developer's laptop and other sessions.

This is infrastructure an organization can operate in its AWS account, with its own repository access and network decisions. It is not a promise that a MicroVM automatically protects every secret inside it. AWS's [coding-agent architecture](https://aws.amazon.com/blogs/compute/secure-code-execution-for-ai-agents-with-aws-lambda-microvms/) puts isolation beside separate governance: its AgentCore Policy layer can check tool calls before an agent acts. An isolated process with unrestricted outbound access and powerful credentials can still send data or make damaging API calls. **Isolation bounds where code runs; policy bounds what it can reach.**

## Why this matters after the code-upload stories

The anxiety is not theoretical. A [researcher's account of ZCode](https://blog.ferstar.org/en/posts/zcode-silent-workspace-snapshot-upload/) described a workspace archive queued for upload without the user's informed consent; Z.ai subsequently apologized and characterized the behavior as a bug. [Reporting on Grok Build](https://www.theverge.com/ai-artificial-intelligence/965600/spacexai-grok-build-repository-upload) also described unexpected full-codebase uploads, after which its operator disabled automatic uploads. Those cases warrant scrutiny of **actual data flows**, rather than a blanket claim that every hosted coding tool steals code.

Docker Kits and Lambda MicroVMs do not magically make a model private. If the agent calls an external model API, repository content may still be sent to that provider as prompt context. If it downloads dependencies or opens a pull request on a third-party service, those are other outbound paths. To keep source within an organization's chosen boundary, a team must select an appropriate model deployment or contract, restrict network egress, scope credentials, and inspect logs and artifacts. The sandbox makes those choices easier to express and enforce; it cannot make them on the team's behalf.

## The next normal for coding agents

Picture a team publishing a pinned agent environment for a Java service. It grants a read-only dependency registry, a scoped repository token, and access to one staging API. A developer assigns an issue; the agent runs in a disposable MicroVM, executes tests, and returns a diff for review. The team can change the model behind that workflow without handing every vendor the same broad machine access. This is a **possible architecture**, not an announced Docker–AWS integration or a turnkey guarantee.

That is the larger movement these releases make visible. Organizations can build their own agent workflow instead of depending entirely on the default workspace and permission model of Codex, Claude Code, Grok, or another vendor. Models still matter, and hosted tools may be convenient. But the durable questions now belong to the organization: **who approved this agent, what was it allowed to see, where did its code run, and what did it send out?** The next useful coding agent will have answers a security reviewer can verify, not just a demo that finishes the ticket.
