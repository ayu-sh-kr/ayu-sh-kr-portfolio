# The race to faster AI inference: Meta, Fireworks and DeepSeek

**Meta and Paradigm have launched a $100,000 prize challenge to make Muse Spark Open run faster**, while Fireworks is promoting DeepSeek generation above **1,521 tokens per second**. DeepSeek has also released DeepInfer, the framework behind its production inference service. This week's announcements put the software running AI models at the centre of the competition.

The shared goal is shorter waits and more work from the available hardware. **Inference** is the process of running a trained model to produce an answer. Improving it can make the same model more responsive and cheaper to serve, without waiting for another generation of model training.

## Meta puts a reward on faster Muse Spark

Announced on **October 22**, the [Muse Spark Open Kernel Challenge](https://openkernelchallenge.dev/) offers **$100,000 in total prizes**. [Paradigm's Matt Huang describes it as a joint Meta and Paradigm challenge](https://x.com/matthuang/status/2113354212642066518); Daniel Gross also [announced the competition](https://x.com/danielgross/status/2113351902402613558). Its stated path is to optimize Muse Spark Open's GPU kernels, then improve how SGLang serves the model.

A **kernel** is a small program that performs an operation on a GPU. SGLang is an inference framework that coordinates those operations and serves requests. That gives contestants two places to find improvements: the calculations themselves and the way the system runs them together.

Meta has already shipped changes here. Its [October 15 Muse Spark Open release](https://research.meta.ai/blog/muse-spark-open) includes auto-tunable **Helion kernels**, which can search for efficient configurations for different workloads and hardware. Meta reports **1.03–3.95× kernel-level speedups**, with a **3% improvement in end-to-end throughput on AMD MI350**.

The [PyTorch engineering post](https://pytorch.org/blog/muse-spark-open/) also describes Helion **megakernels** in SGLang. These combine multiple operations into a single persistent kernel, reducing repeated launches and the gaps between operations. Faster individual operations help, but the 3% system result shows why the whole request path matters: accelerating one part leaves other costs in place.

The challenge is an invitation to push that work further. Its prize pool is an incentive for future improvements, rather than a speedup already achieved.

## Fireworks makes the speed difference visible

Fireworks is demonstrating the application side of the race. It says **DeepSeek V4.1 Flash 1017** runs at more than 1,521 tokens/s on its Ultrafast platform. A token is a piece of text generated by the model; this rate describes how quickly the response is produced.

In the [company's Tetris demonstration](https://x.com/FireworksAI_HQ/status/2112973992097468795), the game was ready in **11 seconds**, with Fireworks claiming a **sevenfold task-time advantage over Claude Opus 5.5**. The October DeepSeek update also [reports shorter outputs and reduced task execution time](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017), illustrating another route to finishing sooner: generate less text to complete the work.

These are related improvements, but different measurements:

| Development | Reported result | Scope |
| --- | --- | --- |
| Fireworks Ultrafast | 1,521+ tokens/s with DeepSeek | Provider-reported generation rate in its demonstration. |
| Tetris comparison with Opus 5.5 | DeepSeek ready in 11 seconds; claimed 7× faster | Completion time for the demonstrated task. |
| Meta's Helion kernels | 1.03–3.95× kernel speedups; 3% end-to-end gain on MI350 | Individual operations versus overall serving throughput. |
| DeepInfer's draft verification | 4–7% throughput gain at its production operating point | Improvement over checking a fixed five-token draft. |

The sevenfold task result does not establish a sevenfold token-rate advantage over Opus. Output length, reasoning settings, startup time and correctness all affect the comparison. Fireworks' streaming figure also belongs to its deployment, rather than every service hosting DeepSeek.

## Where inference is actually getting faster

A request has two main model-processing stages. **Prefill** processes the prompt; **decode** generates the answer. Faster prefill helps the response start sooner. Faster decoding shortens the wait for the rest.

For a coding agent, repeated instructions and repository context can make prompt processing expensive. A **KV cache** retains intermediate attention data so matching context can be reused. DeepSeek's [deployment Q&A](https://github.com/deepseek-ai/DeepInfer/blob/main/doc/inference_deployment_qa.md) describes retaining cache for three days for agents and seven days for chatbot traffic, reducing repeated prefill work when requests hit that cache.

On the generation side, **speculative decoding** drafts several possible next tokens and checks them with the model. DeepInfer's DSpark uses confidence estimates to choose which drafts deserve verification. DeepSeek reports a **4–7% throughput improvement** at its production operating point compared with checking all five draft tokens each time.

Scheduling tackles another delay: hardware sitting idle between steps. DeepInfer overlaps CPU scheduling with GPU execution, while Meta's megakernels reduce boundaries between GPU operations. Both aim to spend more time doing useful work. The [DeepInfer release](https://github.com/deepseek-ai/DeepInfer) exposes core engine features, although parts of the production caching and service infrastructure remain outside it.

> **Inference improves by doing less repeated work, reducing idle time and generating useful results in fewer steps.**

## The prize is a shorter working loop

Meta's challenge, Fireworks' demo and DeepInfer's release approach the same problem from different directions: improve the operations, demonstrate the response speed and make serving techniques available to other developers.

For agents, those gains can accumulate across a sequence of edits, tool calls and checks. Saving time on every generation turn can make an interactive workflow more practical; serving more requests per GPU can reduce its operating cost. External tools and tests still contribute to the wait.

That extends the efficiency competition already visible in [Opus 5.5's pricing and response improvements](/news/claude-opus-5-5-cost-coding/). The next result to watch is whether these faster engines and rewarded optimizations make everyday tasks finish sooner at an affordable price. **A model's capability becomes more useful when an application can afford to wait for it—and afford to run it again.**
